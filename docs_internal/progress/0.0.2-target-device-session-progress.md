## Current Goal

Bind every bridge-backed Ask UI workbench session to a concrete Android Target
Device.

This slice makes `deviceId` part of the startup contract, validates the Target
Device through Flutter tooling, preserves one Target Device per bridge session,
and exposes Target Device connection state in the TopBar and Live App Surface.

## Phase Details

### 1. Product Contract And Issue Split

Issue 1 was carved out as the first tracer bullet for Live App Surface work.
The contract intentionally stops short of proving that `vmServiceUri` came from
the same physical device as `deviceId`; first-version validation only checks
that Flutter currently lists the requested Android Target Device.

Decisions captured for this phase:

- The URL requires `vmServiceUri`, `projectRoot`, and `deviceId`.
- `deviceId` is camelCase only.
- The bridge owns Target Device availability checks.
- A bridge session cannot silently switch Target Devices.
- User-facing failures use stable error codes and short Target Device messages.

### 2. Bridge Target Device Checker

The bridge gained a focused checker for `flutter devices --machine`.

Implemented behavior:

- Runs `flutter devices --machine`.
- Trims the requested `deviceId` before matching.
- Matches `deviceId` exactly and case-sensitively.
- Accepts only devices whose `targetPlatform` starts with `android`, matched
  case-insensitively.
- Treats missing `isSupported` as available.
- Treats `isSupported == false` as unavailable.
- Converts command failure, malformed JSON, and unexpected output shape into
  `FlutterDeviceCheckFailed`.

The checker is covered by `apps/bridge/test/flutter_device_checker_test.dart`.

### 3. Bridge Session Binding And HTTP Errors

Session creation now requires a Target Device before the bridge creates or
reuses a session.

Implemented behavior:

- `POST /api/sessions` rejects missing or blank `deviceId` with
  `missing_session_parameters`.
- Valid sessions store the trimmed `deviceId`.
- Repeated requests for the same `vmServiceUri`, `projectRoot`, and `deviceId`
  reuse the existing session.
- Repeated requests for the same `vmServiceUri` and `projectRoot` with a
  different `deviceId` fail with `device_mismatch_for_session`.
- Target Device not found returns `target_device_not_found`.
- Unsupported Android Target Device returns `target_device_unavailable`.
- Flutter tooling or output failures return `target_device_check_failed`.

User-facing messages:

- `Target Device <deviceId> is not listed by Flutter.`
- `Target Device <deviceId> is not available.`
- `Ask UI could not check Flutter target devices.`
- `VM Service device does not match Target Device <deviceId>.`

Device check failure responses do not expose command output or environment
details. Bridge logs include the command, `deviceId`, error, and stack trace.

### 4. Web URL Bootstrap And Bridge Client

The web startup path now treats Target Device as a required bootstrap value.

Implemented behavior:

- `readSessionBootstrap` requires `deviceId`.
- `device_id` is intentionally not accepted.
- `createBridgeSession` sends `deviceId` to the bridge.
- Bridge request failures preserve the bridge error code and message in
  `BridgeRequestError`.

This keeps browser startup aligned with the bridge API instead of allowing the
web app to create incomplete sessions that fail later.

### 5. Target Device Visible State

The web UI now derives Target Device display text from a small typed model.

Implemented states:

- Incomplete startup: `Device required`.
- Session creation: `Connecting device`.
- Session error: `Device unavailable`.
- Ready session: `Device <deviceId>` in the TopBar and raw `<deviceId>` in the
  Live App Surface context.

Long device ids are displayed with truncation support and the complete value
available through title behavior.

### 6. Workbench Readability Refactor

After Issue 1 landed, `AskUiWorkbench` was split so the next Live App Surface
slice does not add WebSocket lifecycle code to an already large component.

Extracted hooks:

- `useBridgeSession` owns URL bootstrap and bridge session creation.
- `useWidgetTree` owns Widget Tree loading and refresh.
- `useWorkbenchActions` owns Select Widget, Hot Reload, Hot Restart, and SSE
  synchronization.
- `usePanelResize` owns Widget Tree panel resizing.

The session state and Widget Tree state are now separate. `AskUiWorkbench`
acts as a composition component that wires hooks into `TopBar`,
`WidgetTreePanel`, `LiveAppSurface`, and `SelectionNotesPanel`.

## Out Of Scope

- Strict proof that `vmServiceUri` came from the same Android device as
  `deviceId`.
- User-facing configuration for the Flutter executable path.
- Device WebSocket startup.
- Real scrcpy video streaming.
- Device View coordinate mapping.
- Surface Controls.
- Automatic reconnect or Surface retry.

## Notes For Issue 2

Issue 2 should build on the separated workbench structure instead of adding
WebSocket lifecycle code directly back into `AskUiWorkbench`.

The expected next boundary is a `useLiveAppSurface(sessionId)` hook that owns
Device WebSocket connection state, retry, ready metadata, and Device error
codes while `LiveAppSurface` remains primarily presentational.
