## Issue 3: Add Agent Poller Readiness Loop

Type: AFK

## What to build

Add the Agent Session poller lifecycle for one Bridge Session.

The launching Agent Session should be able to long-poll the Bridge Session for the next Chat message. While one poller is waiting, Agent Status is `Agent ready`. Only one active poller is allowed. Additional pollers are rejected. If the waiting poller disconnects before receiving a message, Agent Status returns to `Waiting for agent`.

## Acceptance criteria

- [x] A Bridge Session allows only one active Agent Session poller.
- [x] A second active poller request is rejected rather than replacing the first.
- [x] Polling is indefinite by default.
- [x] Optional timeout exists only for tests or debugging.
- [x] Agent Status becomes `Agent ready` when a poller is waiting.
- [x] Agent Status becomes `Waiting for agent` when a waiting poller disconnects before receiving a message.
- [x] Poller terminology does not appear in product UI.
- [x] Poller output can return a current Chat message payload when available.
- [x] Poller output includes a next-step instruction for the Agent Session.
- [x] Bridge tests cover single active poller enforcement.
- [x] Bridge tests cover waiting poller disconnect.
- [x] Bridge tests cover timeout behavior where applicable.

## Issue 4: Add Plain Text Chat Send And Reply Loop

When Agent Status is `Agent ready`, the developer can send a typed Chat message. The Bridge Session delivers it to the active poller, stores it in Chat History, moves Agent Status to `Agent working`, and the Agent Session can write back either a plain text agent reply or a system message. - [x] Delivery failure during poller handoff makes Send fail and preserves composer text.
- [x] Successful Send appends a `user` message to Chat History.
- [x] Successful Send clears typed composer text.
- [x] Agent Status becomes `Agent working` after the poller takes the message.
- [x] Chat may show a temporary `Agent working...` placeholder.
- [x] Agent reply writes an `agent` message to Chat History.
- [x] Agent error writes a separate `system` message to Chat History.
- [x] Chat History message roles are only `user`, `agent`, and `system`.
- [x] Agent reply and agent error write failures do not continue polling.
- [x] Agent reply success followed by failed continued polling keeps the reply and returns Agent Status to `Waiting for agent`.

- [x] Bridge tests cover send, handoff, reply, error, and Agent Status transitions.
- [x] Web tests cover disabled reasons, working placeholder, plain text send, send failure preservation, and Chat History rendering.

Progress note:

- Partial implementation exists in commit `f03d00c`: web state, background
  capture orchestration, Bridge snapshot API contract, unavailable fallback,
  send wait/timeout handling, and fake-capture tests are in place.
- Production runtime now defaults to `AdbSnapshotCapture`, which uses explicit

## Issue 10: Define Agent Session Command Contract For Reply And Continued Polling

Type: HITL

## What to build

Define and implement the Agent Session Command contract for the Agent Session loop.

The standard CLI command loop should support a combined command shape like `agent poll --agent-reply "..."`: write a plain text agent reply, then continue waiting for the next Chat message. A command-level error path should write a system message and normally continue polling unless explicitly stopped or unable to continue. The command output should guide Codex, Claude Code, or similar agents to process the message, write back a reply or error, and continue polling. HTTP endpoints may remain the underlying transport, but the CLI is the agent-facing contract.

## Acceptance criteria

- [ ] The standard agent loop is poll, process, reply, poll again.
- [ ] A command can write an agent reply and continue polling in one flow.
- [ ] A command can write a system error message.
- [ ] Command-level errors produce `system` messages, not `agent` messages.
- [ ] Normal agent explanations of failed work use `agent` messages.
- [ ] Agent replies are correlated with the user message ID they answer.
- [ ] Agent error messages can be correlated with the user message where applicable.
- [ ] Reply write failure prevents continued polling and returns an error.
- [ ] Error write failure prevents continued polling and returns an error.
- [ ] Agent reply success followed by poll continuation failure keeps the reply and moves Agent Status to `Waiting for agent`.
- [ ] Poller output includes the current message payload.
- [ ] Poller output includes next-step guidance for the agent.
- [ ] The CLI command is the formal Agent Session Command contract.
- [ ] HTTP agent endpoints are treated as the underlying transport for the command.
- [ ] The command terminology is not exposed in the product UI.
- [ ] Manual review confirms the command shape works naturally in the launching agent session.
