## Issue 1: Extract Chat Ingress Parsing

Type: AFK

## What to build

Extract the browser Chat ingress rules from the bridge HTTP server into a focused module.

The bridge should keep the existing Chat and Agent Session HTTP behavior, but Chat message parsing, Selection Comment attachment validation, snapshot ownership checks, and normalized Chat command construction should live behind one small interface. The server should become a thin adapter that decodes JSON, calls the Chat ingress module, maps typed outcomes to HTTP responses, and delegates accepted messages to the existing Bridge Session Chat state.

## Acceptance criteria

- [ ] Existing Chat send, Agent poll, Agent reply, and Agent error HTTP behavior remains compatible.
- [ ] Plain text Chat request validation remains unchanged.
- [ ] Ordered Chat `parts` request validation remains unchanged.
- [ ] Selection Comment attachment validation remains unchanged.
- [ ] Selection Comment snapshot ownership checks still require paths owned by the Bridge Session.
- [ ] Chat message, Selection Comment text, metadata, and batch limits remain enforced.
- [ ] Invalid Chat requests return the same public error codes as before.
- [ ] The new Chat ingress module has focused tests for accepted plain text, accepted Selection Comment attachments, invalid part shapes, limits, and snapshot ownership.
- [ ] Existing bridge server Chat tests continue to pass.
- [ ] `AskUiBridgeServer` no longer owns the detailed Selection Comment parsing implementation.

## Blocked by

None - can start immediately.

## Issue 2: Extract Device WebSocket Session Lifecycle

Type: AFK

## What to build

Extract the Live App Surface Device WebSocket lifecycle from the bridge HTTP server into a focused module.

The bridge should keep the existing `/api/sessions/:sessionId/device` WebSocket contract, including ready metadata, raw H.264 binary chunks, control messages, one-active-WebSocket enforcement, debug fixture behavior, and cleanup semantics. The new module should own the lifecycle around WebSocket upgrade handling after the server resolves the Bridge Session.

## Acceptance criteria

- [ ] The Device WebSocket route remains compatible.
- [ ] Only one active Device WebSocket is allowed per Bridge Session.
- [ ] A second active Device WebSocket still receives `device_already_active`.
- [ ] A new Device WebSocket is allowed after the active one closes.
- [ ] Device control validation still uses the existing control protocol rules.
- [ ] Invalid control messages still return `control-error` without closing the stream.
- [ ] Accepted non-move touch and system key controls are still logged.
- [ ] Device stream startup failure still returns `device_start_failed`.
- [ ] WebSocket close and error paths still close the underlying Device stream.
- [ ] Debug fixture video and debug metadata behavior remains available for tests.
- [ ] The WebSocket stream sink adapter is moved out of `AskUiBridgeServer`.
- [ ] Existing bridge server Device WebSocket tests continue to pass.

## Blocked by

None - can start immediately.

## Issue 3: Extract Bridge Session Event Stream

Type: AFK

## What to build

Extract the Bridge Session Server-Sent Events stream from the bridge HTTP server into a focused module.

The bridge should keep the existing `/api/sessions/:sessionId/events` SSE contract. The event stream module should own initial Select Widget and Chat snapshots, Inspector mode subscriptions, Chat event subscriptions, heartbeat writes, write serialization, and cleanup on disconnect. The server should only resolve the Bridge Session, prepare the response as an SSE transport, and delegate stream orchestration.

## Acceptance criteria

- [ ] The session events route remains compatible.
- [ ] The stream still emits the initial Select Widget mode snapshot.
- [ ] The stream still emits the initial Chat snapshot.
- [ ] Select Widget mode changes still emit session events.
- [ ] Chat History and Agent Status changes still emit session events.
- [ ] Heartbeat behavior remains compatible.
- [ ] SSE writes remain serialized.
- [ ] Inspector and Chat subscriptions are cancelled when the browser disconnects.
- [ ] Select Widget mode snapshot failure still returns `session_events_failed`.
- [ ] Existing bridge server Chat and Select Widget event tests continue to pass.
- [ ] `AskUiBridgeServer` no longer owns the event stream state machine.

## Blocked by

None - can start immediately.

## Issue 4: Extract Bridge Session Creation

Type: AFK

## What to build

Extract Bridge Session creation and Target Device startup validation from the bridge HTTP server into a focused module.

The bridge should keep the existing `POST /api/sessions` contract, but request validation, project root validation, Target Device availability checks, SessionStore creation, device mismatch handling, and typed rejection reasons should be concentrated behind a Bridge Session creation interface. This keeps ADR-0001's Target Device startup contract in one place and leaves the HTTP server as a response-mapping adapter.

## Acceptance criteria

- [ ] Session creation route remains compatible.
- [ ] Missing or blank `vmServiceUri`, `projectRoot`, or `deviceId` still returns `missing_session_parameters`.
- [ ] Invalid project root still returns `invalid_project_root`.
- [ ] Target Device checker failures still return `target_device_check_failed` without exposing command internals in the response.
- [ ] Missing Target Device still returns `target_device_not_found`.
- [ ] Unavailable Target Device still returns `target_device_unavailable`.
- [ ] Reusing the same Flutter app session with a different Target Device still returns `device_mismatch_for_session`.
- [ ] Successful creation still returns `sessionId`, `targetDevice`, and `readOnly`.
- [ ] Bridge Session creation has focused tests for typed success and rejection outcomes.
- [ ] Existing bridge server session tests continue to pass.
- [ ] `AskUiBridgeServer` no longer owns the detailed Target Device startup validation implementation.

## Blocked by

None - can start immediately.

## Issue 5: Thin The Bridge HTTP Adapter

Type: AFK

## What to build

Thin `AskUiBridgeServer` after the deeper bridge modules have been extracted.

The server should remain the transport adapter for HTTP, WebSocket, CORS, JSON responses, and route dispatch, but route handlers should delegate domain behavior to the extracted Chat ingress, Device WebSocket session, Bridge Session event stream, and Bridge Session creation modules. Avoid introducing a generic router or helper abstraction that is shallow; only consolidate repeated request mechanics when it reduces caller knowledge and keeps behavior behind a clearer interface.

## Acceptance criteria

- [ ] `AskUiBridgeServer` remains the public server entrypoint.
- [ ] Existing HTTP and WebSocket routes remain compatible.
- [ ] Repeated JSON object decoding is consolidated where it reduces route-handler noise.
- [ ] Repeated Bridge Session lookup and `session_not_found` response mapping is consolidated where it reduces route-handler noise.
- [ ] Repeated JSON response writing remains centralized.
- [ ] CORS and `OPTIONS` behavior remains compatible.
- [ ] Route handlers read as transport adapters rather than owning Chat, Device, event stream, or Session creation rules.
- [ ] No broad generic router is introduced unless it demonstrates clear leverage over the existing route list.
- [ ] Existing bridge server tests continue to pass.
- [ ] `dart test` from `apps/bridge` passes.
