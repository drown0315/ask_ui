## Issue 1: Add Reply-To Correlation To Agent Chat Messages

Type: AFK

## Parent

https://github.com/drown0315/ask_ui/issues/11

## What to build

Add first-class reply-to correlation for Agent Session-authored Chat messages.

Agent replies should record which user Chat message they answer. Command-level system errors may record the user Chat message they relate to. The Bridge Session should validate reply-to references through the existing agent reply and error paths, serialize the correlation in Chat History, and preserve the existing poll, send, and Agent Status behavior.

## Acceptance criteria

- [x] Chat messages can include a top-level `replyToMessageId` field.
- [x] User messages do not include `replyToMessageId`.
- [x] Agent messages require `replyToMessageId`.
- [x] System messages may include `replyToMessageId`.
- [x] `replyToMessageId` is not stored inside message context.
- [x] Agent reply writes fail when `replyToMessageId` is missing.
- [x] Agent reply writes fail when `replyToMessageId` does not exist.
- [x] Agent reply writes fail when `replyToMessageId` points to a non-user message.
- [x] Agent error writes accept no `replyToMessageId`.
- [x] Agent error writes accept a valid user-message `replyToMessageId`.
- [x] Agent error writes fail when a provided `replyToMessageId` does not exist.
- [x] Agent error writes fail when a provided `replyToMessageId` points to a non-user message.
- [x] Multiple agent or system messages may point to the same user message.
- [x] Agent reply and error text validation uses trimmed non-empty checks but stores the original text.
- [x] Agent reply and error text remain limited to 4000 characters.
- [x] Bridge tests cover serialization, validation failures, optional system-message correlation, and multiple follow-up messages for one user message.

## Blocked by

None - can start immediately.

## Issue 2: Add Agent Command Pure Poll CLI

Type: AFK

## Parent

https://github.com/drown0315/ask_ui/issues/11

## What to build

Add the first Agent Session Command CLI path for pure polling.

The bridge command entrypoint should support `agent poll` for waiting on the next Chat message from a Bridge Session. The command should resolve connection context from explicit flags or environment variables, call the existing agent poll transport, and return a single JSON object suitable for a coding agent to consume.

## Acceptance criteria

- [x] The existing bridge server start command remains compatible.
- [x] The command entrypoint supports `agent poll`.
- [x] `agent poll` reads Bridge URL from `--base-url` first, then `ASK_UI_BRIDGE_URL`.
- [x] `agent poll` reads Bridge Session ID from `--session-id` first, then `ASK_UI_SESSION_ID`.
- [x] Missing Bridge URL fails with `missing_bridge_url`.
- [x] Missing Bridge Session ID fails with `missing_session_id`.
- [x] The command does not scan ports.
- [x] The command does not read browser URLs.
- [x] The command does not use repo-local state files.
- [x] The command does not expose a CLI timeout flag.
- [x] The command supports `agent poll --once` for a one-message pure poll.
- [x] Pure poll success writes one JSON object to stdout.
- [x] Pure poll failure writes one JSON object to stderr and exits non-zero.
- [x] Pure poll success includes `status`, `message`, and `nextStep`.
- [x] `nextStep` identifies the message to process and tells the Agent Session to reply with `--reply-to`.
- [x] `agent_poll_already_active` is treated as command failure.
- [x] `agent_poll_already_active` does not write a system Chat message.
- [x] CLI tests cover flag/env precedence, missing configuration, pure poll output, active-poller conflict, and absence of timeout/state discovery behavior.

## Blocked by

None - can start immediately.

## Issue 3: Add Agent Reply Command Once Path

Type: AFK

## Parent

https://github.com/drown0315/ask_ui/issues/11

## What to build

Add the one-shot Agent Session Command path for writing an agent reply.

The command should support `agent poll --reply-to <message-id> --agent-reply <text> --once`. It should validate the command arguments, write one correlated `agent` message through the existing transport, output `writtenMessage`, and exit without starting a continued poll.

## Acceptance criteria

- [x] `agent poll --agent-reply <text> --once` requires `--reply-to`.
- [x] `--reply-to` uses the CLI option name, while JSON uses `replyToMessageId`.
- [x] `--agent-reply` and `--agent-error` are mutually exclusive.
- [x] Agent reply text is supplied only through `--agent-reply`.
- [x] The command does not support stdin variants for reply text.
- [x] Whitespace-only reply text fails with `empty_chat_message`.
- [x] Over-limit reply text fails with `chat_message_too_long`.
- [x] Invalid or missing reply-to references fail with `invalid_reply_to_message`.
- [x] Reply write failures do not start polling.
- [x] Reply write success with `--once` writes one JSON object to stdout.
- [x] Reply write success with `--once` includes `status`, `writtenMessage`, `message: null`, and `nextStep`.
- [x] `writtenMessage` includes role `agent` and the top-level `replyToMessageId`.
- [x] The `nextStep` says no further polling was requested.
- [x] CLI tests cover argument validation, reply text validation, successful `writtenMessage` output, and no continued poll when `--once` is present.

## Blocked by

- Issue 1: Add Reply-To Correlation To Agent Chat Messages
- Issue 2: Add Agent Command Pure Poll CLI

## Issue 5: Add Continued Polling After Agent Reply Or Error

Type: AFK

## Parent

https://github.com/drown0315/ask_ui/issues/11

## What to build

Make Agent Session Command reply and error writes continue polling by default.

When `--once` is absent, `agent poll --agent-reply` and `agent poll --agent-error` should first write the agent-authored Chat message, then start the next poll in the same command process. The command should wait until the next user Chat message arrives, return both the written message and the next message, and clearly report partial success if continuation fails after the write.

## Acceptance criteria

- [x] `agent poll --reply-to <message-id> --agent-reply <text>` writes an agent message and then waits for the next user message.
- [x] `agent poll --agent-error <text>` writes a system message and then waits for the next user message.
- [x] `agent poll --reply-to <message-id> --agent-error <text>` writes a correlated system message and then waits for the next user message.
- [x] Continued polling happens in the same command process.
- [x] While continued polling waits, Agent Status becomes `Agent ready`.
- [x] Continued poll success writes one JSON object to stdout.
- [x] Continued poll success includes `status`, `writtenMessage`, `message`, and `nextStep`.
- [x] `writtenMessage` confirms the reply or system message that was already stored.
- [x] `message` contains the next user Chat message payload.
- [x] `nextStep` tells the Agent Session to process the returned `message`.
- [x] Reply write failure prevents continued polling and returns an error.
- [x] Error write failure prevents continued polling and returns an error.
- [x] Agent reply success followed by poll continuation failure keeps the reply.
- [x] Agent error success followed by poll continuation failure keeps the system message.
- [x] Poll continuation failure exits non-zero with `poll_continuation_failed`.
- [x] Poll continuation failure writes a JSON error to stderr that includes `writtenMessage`.
- [x] Poll continuation failure instructs the Agent Session not to retry the written message.
- [x] Bridge and CLI tests cover successful continued polling and partial-success failure for both reply and error paths.

## Blocked by

- Issue 3: Add Agent Reply Command Once Path
- Issue 4: Add Agent Error Command Once Path

## Issue 6: Harden Agent Session Command Contract

Type: AFK

## Parent

https://github.com/drown0315/ask_ui/issues/11

## What to build

Harden the complete Agent Session Command contract after the main loop is working.

This slice should lock down the final machine-readable behavior: the error-code vocabulary, JSON-only output, scenario-specific next-step guidance, unsupported flags and inputs, and the absence of command terminology in product UI.

## Acceptance criteria

- [x] Success output is always a single JSON object on stdout.
- [x] Failure output is always a single JSON object on stderr with a non-zero exit code.
- [x] The command does not emit human-readable banners, progress logs, or explanatory prose on stdout.
- [x] The command does not support `--json`.
- [x] The command does not support stdin text inputs.
- [x] The command does not support a CLI timeout flag.
- [x] The command does not use repo-local session state.
- [x] The command does not scan ports or discover sessions automatically.
- [x] The supported error code set includes `missing_bridge_url`, `missing_session_id`, `invalid_arguments`, `invalid_reply_to_message`, `empty_chat_message`, `chat_message_too_long`, `session_not_found`, `agent_poll_already_active`, `bridge_request_failed`, and `poll_continuation_failed`.
- [x] Unknown or invalid argument combinations fail with `invalid_arguments`.
- [x] Scenario-specific `nextStep` is present for pure poll success, write-once success, write-and-continue success, and poll continuation failure.
- [x] Agent command, poller, and transport terminology does not appear in product UI.
- [x] Manual review confirms the command shape works naturally in the launching Agent Session.
- [x] Tests cover the final error-code vocabulary, unsupported flags, JSON-only output behavior, and no command terminology leaks into web UI text.

## Blocked by

- Issue 5: Add Continued Polling After Agent Reply Or Error
