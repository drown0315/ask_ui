## Issue 1: Add Ask UI Version Manifest And Local Metadata

Published issue: https://github.com/drown0315/ask_ui/issues/33

## Parent

https://github.com/drown0315/ask_ui/issues/32

## What to build

Add the version model that lets Ask UI describe a compatible installer, bridge,
runtime, and skill set. The slice should define a version manifest shape, add
local project metadata for the installed Ask UI set, and expose focused parsing
and validation behavior that later installer, update, doctor, and release checks
can reuse.

## Acceptance criteria

- [x] Ask UI has a documented version manifest shape that includes latest,
      minimum supported, installer, bridge, runtime, and skill versions.
- [x] Ask UI has a local project metadata shape for recording the installed
      Ask UI version set.
- [x] Version parsing and compatibility checks are testable without network,
      pub, npm, Flutter, or GitHub access.
- [x] Missing, malformed, mixed-version, and compatible-version cases have
      externally observable test coverage.

## Blocked by

None - can start immediately.

## Implementation status

Completed locally with the bridge `versions` module and focused tests covering
manifest parsing, local metadata parsing, structured validation failures, and
mixed-version compatibility checks.

## Issue 4: Implement Full Install Bootstrap

Published issue: https://github.com/drown0315/ask_ui/issues/36

## Parent

https://github.com/drown0315/ask_ui/issues/32

## What to build

Make `npx ask-ui install` perform the Ask UI bootstrap for a Flutter project.
It should install or upgrade the bridge, install the Ask UI skill through
`npx skills add https://github.com/drown0315/ask_ui/tree/main/skills/ask-ui`,
run diagnostics, write local metadata, and print the next `ask_ui_bridge launch`
command. `npx ask-ui install` should perform installation by default;
`npx ask-ui install --dry-run` should only print the setup plan. The installer
should not automatically add the `ask_ui_runtime` dependency to the target
Flutter project, should not pass an agent selector to the Skills CLI, and should
not support a separate `--yes` approval option. Normal output should be
human-readable; `--json` should opt into machine-readable JSON output.

## Acceptance criteria

- [x] The installer invokes bridge installation through pub global activation
      and reports activation failures clearly.
- [x] The installer installs the Ask UI skill through `npx skills add` without
      an agent selector and reports skill installation failures without hiding
      earlier setup results.
- [x] `--dry-run` prints the bridge, skill, metadata, and diagnostics actions without
      executing external commands.
- [x] `--yes`, `-y`, and `--agent` are rejected as invalid installer arguments.
- [x] Default install, dry-run, and error output is human-readable, while
      `--json` returns stable JSON output for scripts and agents.
- [x] Successful install records local metadata, runs diagnostics, and prints a
      launch command for the target project.
- [x] Tests verify command invocation, arguments, partial failures, idempotent
      reruns, metadata writes, diagnostics, and final output using fake external
      tools.

## Blocked by

- https://github.com/drown0315/ask_ui/issues/34
- https://github.com/drown0315/ask_ui/issues/35

## Implementation status

Completed locally in the npm installer. `npx ask-ui install` now performs the
bridge activation, Skills CLI install, local metadata write, diagnostics run,
and launch command output. `npx ask-ui install --dry-run` prints the setup plan
without executing commands. Normal output is human-readable, and `--json`
returns machine-readable JSON. Removed installer arguments such as `--yes`, `-y`,
and `--agent` now return stable invalid-argument output.

## Issue 5: Document Manual Skills CLI Install Path

Published issue: https://github.com/drown0315/ask_ui/issues/37

## Parent

https://github.com/drown0315/ask_ui/issues/32

## What to build

Document and validate the manual install path for users who want to manage each
step themselves. The documented "Other Install Ways" path should install the
bridge through pub and install the Ask UI skill through the public Skills CLI
repository URL. The Ask UI installer should not add a separate `--skill-only`
mode, and it should not expose an Ask UI-specific `--agent` option.

## Acceptance criteria

- [x] Documentation presents `npx ask-ui install` as the Recommended Install.
- [x] Documentation presents a single "Other Install Ways" command sequence:
      `dart pub global activate ask_ui_bridge` followed by
      `npx skills add https://github.com/drown0315/ask_ui/tree/main/skills/ask-ui`.
- [x] Documentation does not split the manual path into separate Bridge Only or
      Skill Only sections.
- [x] Installer argument tests reject `--skill-only` and `--agent`.
- [x] Tests or release checks verify the documented Skills CLI command stays in
      sync with the installer skill command.

## Blocked by

- https://github.com/drown0315/ask_ui/issues/35

## Implementation status

Completed locally with public README install documentation for Recommended
Install and Other Install Ways, installer argument coverage for removed
skill/agent modes, and a regression test that compares the documented Skills CLI
command with the installer dry-run action.

## Issue 6: Implement Unified Ask UI Update Command

Published issue: https://github.com/drown0315/ask_ui/issues/38

## Parent

https://github.com/drown0315/ask_ui/issues/32

## What to build

Add `npx ask-ui update` as the main update command for the full Ask UI version
set. The command should update the bridge, skill, and local metadata together,
then run diagnostics so users know whether the updated setup is usable. It
should check runtime compatibility through diagnostics, not edit the target
Flutter project's runtime dependency.

## Acceptance criteria

- [ ] `npx ask-ui update` reads the version manifest and local metadata to
      decide what needs updating.
- [ ] The command updates bridge and skill through the same external
      mechanisms used by install.
- [ ] The command handles already-current setups as a successful no-op with
      useful output.
- [ ] Partial update failures report what changed, what failed, and what the
      user should do next.
- [ ] Successful updates run diagnostics and refresh local metadata.
- [ ] Tests cover complete update, no-op update, mixed-version update, partial
      failures, and post-update diagnostics.

## Issue 7: Surface Rate-Limited Update Notifications

Published issue: https://github.com/drown0315/ask_ui/issues/39

## Parent

https://github.com/drown0315/ask_ui/issues/32

## What to build

Make normal Ask UI commands surface available updates without blocking valid
work. Diagnostics and launch should perform rate-limited update checks, show the
current and latest versions when an update exists, and tell the user to run
`npx ask-ui update`.

## Acceptance criteria

- [ ] Diagnostics can report an available update from the version manifest.
- [ ] Launch can surface an available update without blocking a valid launch
      path.
- [ ] Update checks are rate-limited so repeated launches do not repeatedly hit
      the network.
- [ ] Offline, unavailable, or malformed update checks do not prevent normal
      local diagnostics or launch behavior.
- [ ] The Ask UI skill workflow delegates setup and update status to
      diagnostics instead of duplicating version logic.
- [ ] Tests cover available update, no update, rate-limited check, offline
      check, malformed manifest, doctor output, launch output, and skill text.
