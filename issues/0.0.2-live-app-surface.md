## Issue 1: Require Target Device For Bridge Sessions

Type: AFK

Status: Completed in `88fb256 feat: require target device for sessions`.

Follow-up structure refactor: `15c9f9d chore: split workbench state hooks`.

## What to build

Require every bridge-backed Ask UI session to be bound to a concrete Target Device.

When the web app starts, it should require `vmServiceUri`, `projectRoot`, and `deviceId` URL parameters. The web app should pass the Target Device to the bridge session creation request, and the bridge should validate that the requested `deviceId` is visible as an Android device in `flutter devices --machine`.

This slice proves the startup path from URL parameters through web session bootstrap, bridge session creation, Target Device availability checking, and user-visible TopBar and Live App Surface connection state.

## Acceptance criteria

- [x] The web app reads `deviceId` from the URL using camelCase only.
- [x] Missing `vmServiceUri`, `projectRoot`, or `deviceId` keeps the workbench in an incomplete startup state.
- [x] The bridge rejects session creation requests with missing or empty `deviceId`.
- [x] The bridge stores `deviceId` on the bridge session.
- [x] Repeated session creation for the same `vmServiceUri`, `projectRoot`, and `deviceId` reuses the existing bridge session.
- [x] Repeated session creation for the same `vmServiceUri` and `projectRoot` with a different `deviceId` fails with `device_mismatch_for_session`.
- [x] `device_mismatch_for_session` uses the message `VM Service device does not match Target Device <deviceId>.`
- [x] `device_mismatch_for_session` exposes `expectedDeviceId` and `requestedDeviceId`.
- [x] The bridge runs `flutter devices --machine` for every session creation request.
- [x] Device matching trims leading and trailing whitespace from `deviceId` and then performs a case-sensitive exact id match.
- [x] The bridge accepts only matching devices whose `targetPlatform` starts with `android`, case-insensitively.
- [x] Devices with `isSupported == false` fail with `target_device_unavailable`.
- [x] Devices with missing `isSupported` are treated as available.
- [x] Empty device lists and missing exact matches fail with `target_device_not_found`.
- [x] Flutter command failure, malformed JSON, or unexpected machine output fails with `target_device_check_failed`.
- [x] Device check failures log the command, `deviceId`, error, and stack trace.
- [x] Device check failure HTTP responses do not expose stdout, stderr, environment variables, or the command.
- [x] `target_device_not_found` uses the message `Target Device <deviceId> is not listed by Flutter.`
- [x] `target_device_unavailable` uses the message `Target Device <deviceId> is not available.`
- [x] `target_device_check_failed` uses the message `Ask UI could not check Flutter target devices.`
- [x] The TopBar labels device states as `Device required`, `Connecting device`, `Device unavailable`, and `Device <deviceId>`.
- [x] The Live App Surface labels incomplete, creating, error, and ready states consistently with the Target Device language.
- [x] Long Target Device ids truncate visually with the complete id available through title or tooltip behavior.
- [x] Existing Flutter Widget Tree session behavior still works for valid sessions.
- [x] `apps/web` build still passes.

## Blocked by

None - can start immediately.

- [x] The shell sends a `ready` message with `deviceId`, `screenWidth`, `screenHeight`, `maxFps`, `videoCodec`, and `controlReady: true`.

- [x] The Live App Surface ready context shows the raw `<deviceId>`.
- [x] Device startup failures show a retry path.
- [x] Runtime Device disconnects show `Device disconnected.` and a retry path.
- [x] Retry reuses the existing bridge session.
- [x] Retry does not create a new bridge session.
- [x] Device startup failures use `device_start_failed`.
- [x] Device runtime failures use `device_failed`.
- [x] Detailed bridge Device logs are available for debugging but are not rendered as high-frequency primary UI.

## Issue 3: Make Device View And Surface Controls Interactive In Shell

Type: AFK

## What to build

Make the fake-metadata Live App Surface interactive through the same control protocol the real scrcpy Surface will use.

The web app should render a Device View that fits the metadata screen size into the available center surface, map pointer input back to Target Device coordinates, ignore letterboxed areas, and send touch and system-key messages through the Device WebSocket. The bridge shell should validate those messages and return `control-error` for protocol mistakes without closing the WebSocket.

This slice proves Device View layout, coordinate mapping, Surface Controls, Select Widget mode compatibility, and the control protocol before real device control is connected.

## Acceptance criteria

- [x] The Live App Surface includes both Device View and Surface Controls.
- [x] Device View is the video area that receives mapped pointer input.
- [x] Surface Controls are outside the Device View coordinate space.
- [x] Back, Home, and Recents controls are displayed below the Device View, not as an overlay.
- [x] No Power, Menu, or extra Android system controls are added in this slice.
- [x] Device View scales the metadata `screenWidth` and `screenHeight` to fit the available center surface.
- [x] Device View allows small device views to scale up.
- [x] `screenWidth` and `screenHeight` come from bridge metadata, not canvas backing size or CSS layout.
- [x] Pointer events in letterboxed or empty areas are ignored.
- [x] Pointer coordinates inside the visible Device View are mapped back into metadata screen coordinates.
- [x] Metadata changes cancel in-progress pointer gestures.
- [x] Touch control messages use `type: "touch"` with actions `down`, `move`, `up`, and `cancel`.
- [x] Web and bridge define centralized protocol action types instead of scattering string literals.
- [x] Long press and swipe are expressed through pointer streams, not separate protocol events.
- [x] Pointer move messages are throttled around 16ms.
- [x] Pointer ids are constrained to `0..0xffffffff`.
- [x] Touch coordinates are valid in the inclusive ranges `0..screenWidth` and `0..screenHeight`.
- [x] Out-of-range touch coordinates return `control-error` and are not clamped.
- [x] Invalid `screenWidth` or `screenHeight` returns `control-error`.
- [x] `cancel` maps to the same release behavior as `up` in the bridge shell.
- [x] System key messages use `type: "systemKey"` with keys `back`, `home`, and `recents`.
- [x] Invalid system keys return `control-error`.
- [x] Unknown control message types return `control-error`.
- [x] Invalid JSON returns `control-error`.
- [x] Legal control messages do not require ACK messages.
- [x] `control-error` does not close the Device WebSocket.
- [x] Surface Controls are disabled until `controlReady` is true.
- [x] Surface Controls remain available during Select Widget mode once control is ready.
- [x] Device View pointer input continues to reach the Target Device during Select Widget mode.
- [x] Back, Home, and Recents do not automatically exit Select Widget mode.
- [x] `apps/web` build still passes.

## Issue 4: Render Fixture H264 Video Through WebCodecs

Type: AFK

Status: Completed in working tree.

## What to build

Render fixture H.264 video through the same WebSocket binary path that the real scrcpy stream will use.

The bridge shell should be able to send raw H.264 Annex B binary chunks over the Device WebSocket. The web app should parse Annex B chunks in a dedicated media module, assemble access units, decode with WebCodecs, render frames inside the Device View, and report a clear unsupported-browser state when WebCodecs is unavailable.

This slice proves the binary video path, WebCodecs integration, parser behavior, first-frame transition, and low-latency frame handling without requiring a real Android device.

## Acceptance criteria

- [x] One Device WebSocket carries both text JSON protocol messages and binary H.264 data.
- [x] Binary Device WebSocket messages are treated as raw H.264 Annex B chunks.
- [x] The shell can send fixture H.264 chunks through the Device WebSocket.
- [x] The web app owns Annex B parsing and access-unit assembly.
- [x] H.264 parsing and access-unit assembly live in a dedicated media module rather than a React component.
- [x] The Device View transitions from `Waiting for video` after the first decoded frame is rendered.
- [x] WebCodecs is the only first-version decode path.
- [x] Browsers without required WebCodecs support show a clear WebCodecs unavailable error.
- [x] No MSE, fMP4, WebRTC, Broadway, or TinyH264 fallback is added.
- [x] Low-latency decoding prioritizes the latest frame.
- [x] Decode queue pressure may drop delta access units.
- [x] Parser tests cover Annex B start codes.
- [x] Parser tests cover NAL units split across chunks.
- [x] Parser tests cover SPS/PPS handling.
- [x] Parser tests cover IDR access-unit assembly.
- [x] Parser tests cover malformed stream handling.
- [x] Parser tests use saved real `.h264` samples when available.
- [x] Byte fixtures cover critical parser behavior when real samples are unavailable.
- [x] `apps/web` build still passes.

## Issue 5: Connect Real Scrcpy Surface Stream

Type: AFK

## What to build

Replace the fixture Device WebSocket shell with a real bridge-owned Android scrcpy stream.

The bridge should start and own the official scrcpy server for the Target Device, manage ADB reverse or forward state, connect video and control sockets, forward raw H.264 Annex B chunks to the web app, translate Surface control messages to device input, and clean up all Device resources immediately on close, cancellation, startup failure, or runtime failure.

This slice proves the real Live App Surface loop: Target Device screen visible in the web Device View, pointer input and Surface Controls delivered to the Android device, and lifecycle ownership kept inside the bridge.

## Acceptance criteria

- [ ] The bridge uses a project-controlled official scrcpy server jar.
- [x] The bridge does not use a desktop scrcpy CLI window.
- [x] The web app never runs ADB.
- [x] The web app never encodes scrcpy binary control messages directly.
- [x] The bridge owns ADB reverse or forward state for the Surface.
- [x] The bridge owns scrcpy server lifecycle for the Surface.
- [x] The bridge connects and owns scrcpy video and control sockets.
- [x] The bridge sends `ready` only after both video and control paths are ready.
- [x] Ready metadata includes the real `deviceId`, `screenWidth`, `screenHeight`, `maxFps`, `videoCodec`, and `controlReady: true`.
- [x] `screenWidth` and `screenHeight` come from bridge, device, or video metadata.
- [x] Scrcpy server version is logged by the bridge.
- [x] Scrcpy server version is not included in Surface ready metadata.
- [x] Raw H.264 Annex B chunks from scrcpy are forwarded as binary WebSocket messages.
- [ ] The web app renders the real Target Device screen in the Device View.
- [x] Touch `down`, `move`, `up`, and `cancel` messages control the Target Device.
- [x] Bridge maps `cancel` to release behavior.
- [x] System key `back`, `home`, and `recents` messages control Android navigation.
- [x] Bridge maps `recents` to Android app-switch behavior internally.
- [x] Invalid control messages still return `control-error` without closing the Device WebSocket.
- [x] Underlying video socket failures fail the whole Device session.
- [x] Underlying control socket failures fail the whole Device session.
- [x] Startup failures use `device_start_failed`.
- [x] Runtime failures use `device_failed`.
- [x] Device WebSocket close cleans up scrcpy server resources.
- [x] Device WebSocket close cleans up video and control sockets.
- [x] Device WebSocket close cleans up ADB reverse or forward state.
- [x] Startup cancellation cleans up partially initialized Device resources.
- [x] Startup failure cleans up partially initialized Device resources.
- [x] Runtime failure cleans up Device resources before allowing retry.
- [x] Retry after failure can start a fresh Surface for the same bridge session.
- [x] Multiple simultaneous Device WebSocket clients or fan-out remain out of scope.
- [x] `apps/web` build still passes.

## Issue 6: Validate Live App Surface On Real Target Device

Type: HITL

## What to build

Validate the completed Live App Surface on a real Android Target Device or emulator.

This issue should confirm that the end-to-end experience matches the PRD in the actual browser and device environment: the Target Device is visible, the Device View scales correctly, pointer interaction and Android navigation work, Select Widget mode remains compatible, and disconnect or retry behavior is understandable.

This slice is HITL because the final visual and interaction quality depends on a real device stream and human-observable behavior.

## Acceptance criteria

- [ ] Ask UI starts successfully with valid `vmServiceUri`, `projectRoot`, and `deviceId`.
- [ ] Ask UI rejects missing or invalid Target Device inputs with the expected user-visible states.
- [ ] The TopBar clearly shows the current Target Device state and `deviceId`.
- [ ] The Live App Surface automatically starts when the bridge session is ready.
- [ ] The Device View displays the real Android Target Device screen.
- [ ] The Device View scales to fit the available center surface without overlapping Surface Controls.
- [ ] Small device views can scale up and remain usable.
- [ ] Letterboxed or empty areas do not send touch input.
- [ ] Clicks land on the expected point in the Target Device.
- [ ] Long press works through pointer down and delayed pointer up.
- [ ] Swipe and drag work through pointer move streams.
- [ ] Back, Home, and Recents controls operate the Target Device.
- [ ] Surface Controls remain available during Select Widget mode.
- [ ] Back, Home, and Recents do not exit Select Widget mode automatically.
- [ ] Select Widget mode still sends Device View pointer input to the Target Device.
- [ ] WebCodecs unavailable behavior is clear in an unsupported browser or simulated unsupported state.
- [ ] Startup Surface failure shows a retry path.
- [ ] Runtime Surface disconnect shows a retry path.
- [ ] Retry reuses the existing bridge session.
- [ ] Closing or unmounting the Surface does not leave stale scrcpy or ADB state that blocks the next connection.
- [ ] Playwright or browser verification covers the visible Live App Surface layout.
- [ ] Real-device validation covers the final video and interaction behavior.
