# Live App Surface WebSocket Protocol

Ask UI will run the Live App Surface through a bridge-owned WebSocket under the existing bridge session, for example `/api/sessions/:sessionId/device-surface`. The bridge session already binds `vmServiceUri`, project root, and `deviceId`, so the Surface WebSocket consumes that binding instead of accepting another device id from the web app.

The first version uses one WebSocket for one Live App Surface. Binary frames carry raw H.264 Annex B bytes from the official scrcpy server, and text JSON frames carry status, metadata, touch input, Android system key commands, logs, and errors. A bridge session allows only one active Surface WebSocket; a second connection should fail with `device_surface_already_active`.

The bridge sends a `ready` JSON message after both video and control paths are ready. It includes complete Surface metadata: `deviceId`, `screenWidth`, `screenHeight`, `maxFps`, `videoCodec`, and `controlReady: true`. Later screen size or orientation changes use a complete `metadata` message with the same metadata fields. The web app uses `screenWidth` and `screenHeight` as the device/video coordinate space, scales the visible Surface view to fit the available UI area, ignores pointer events outside the visible video rect, and maps pointer coordinates back into that screen coordinate space before sending input.

Touch input is sent as a low-level pointer stream rather than gesture-level commands. Web actions use string actions such as `down`, `move`, `up`, and `cancel`; the bridge maps those to scrcpy touch control messages, with `cancel` releasing the pointer like `up`. Back, Home, and Recents are semantic `systemKey` commands sent through the same WebSocket and mapped by the bridge to the appropriate Android control event.

Invalid control messages should return a `control-error` JSON message without closing the Surface WebSocket. Protocol mistakes such as malformed JSON, unsupported control message types, invalid touch fields, or invalid system keys should not tear down the video stream; underlying video/control socket failures still fail the whole Surface session.

The first version keeps lifecycle strict. The Surface starts automatically when the bridge session is ready, retries are manual, and there is no automatic reconnect. If the Surface WebSocket closes, or if either the scrcpy video socket or control socket fails, the bridge cleans up the scrcpy server process, sockets, ADB reverse/forward state, parser buffers, and Surface session state. Startup failures use `device_surface_start_failed`; runtime failures use `device_surface_failed`; detailed phase information belongs in bridge logs.

WebCodecs is the only first-version decode path. The web app owns Annex B parsing and access-unit assembly in a media module, uses low-latency dropping to chase the latest frame, and reports a browser error when WebCodecs is unavailable instead of falling back to MSE/fMP4. Runtime diagnostics such as FPS, dropped frames, queue size, and server logs may be collected for debugging, but they should not be rendered as high-frequency primary UI.

Implementation should proceed in two tracer bullets. First, build a Surface WebSocket shell that runs under a bridge session, emits fake `ready` and `metadata` messages, validates incoming `touch` and `systemKey` messages, supports retry/error UI, and verifies view scaling and coordinate mapping. Then replace the fake stream with the real scrcpy/WebCodecs path: official scrcpy server lifecycle, raw H.264 binary chunks, WebCodecs parsing/decoding, touch/system key execution, and cleanup.
